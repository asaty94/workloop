# 作業の進め方（メインエージェント）

リポジトリのファイルを変える依頼は、変更の大小にかかわらず「作業」とする。作業は業務（計画・仕様・実装・検証）のどの段階でも行う。業務の構成とファイルの置き場所は `layout` スキルに従う。

依頼を受けたメインエージェント（main）は、**ファイルを変える前に、定義（手順 1）から始める。**

## 役割

作業の各段階とエージェントを一対一に対応させない。main が全体の文脈を保持し、自ら実行・検証・確認を担うか、必要に応じてサブエージェントへ委ねるかを判断する。3 種類すべてを呼ぶことや、段階ごとの起動は必須としない。別エージェントを使えない環境では main が各役割を担う。

| 役割 | 担い手 | 責任 |
|---|---|---|
| main | AI | 目的・完了条件・制約・進捗を保持し、作業、委任の判断、結果の統合、Issue・PR・ログの管理、担当者への説明 |
| execution | AI（サブエージェント） | 切り出された範囲の実装・調査。変更と結果、未完了の事項を main へ返す（`execution` スキル） |
| verification | AI（サブエージェント） | 委ねられた検証を行い main へ返す（`verification` スキル） |
| confirmation | AI（サブエージェント） | 委ねられた確認を行い main へ返す（`confirmation` スキル） |
| 担当者 | 人 | main を動かす。レビュー項目に答え、マージを判断する |
| レビュアー | 人 | 担当者から回されたレビュー項目に答える。人数に制限はない |

担当者とレビュアーは、確認に AI を使ってよい。役割ごとの指示の置き場所と CLI の設定は、作業対象リポジトリの `specification/業務/実施/エージェント設定.md` に従う。

### 委任の判断

- 切り出せる実装・調査や並列作業 → execution が候補。
- 複雑な仕様、広い影響、安全性の判断など、独立した見直しが有益なとき → verification・confirmation が候補。
- その作業で必要かを判断する。小さな作業は main だけで完結してよい。
- 委任しても全体の判断と説明の責任は main に残る。戻った結果を依頼と照合して取り込む。
- 自ら担う場合も該当するスキル（`execution`・`verification`・`confirmation`）に従い、検証・確認を行った範囲と未確認の範囲を明示する。

### 委任時に渡すもの

- 目的と完了条件
- 必要な制約・背景
- 担当範囲
- 対象ブランチと差分
- 関連する Issue・PR
- 変更を伴う並列作業では、担当ファイルを分け、他の担当の変更を取り消さないよう伝える。

サブエージェントは再委任、全体の Issue・PR・ログの管理、マージを行わない。

## 権限

main は次の操作を、担当者に聞かずに、作業の流れの中で必要になった時点で行う。

- Issue の作成と要件へのチェック
- Issue の blocked by へのブロックする Issue の追加（手順 1）
- Issue の assignee への担当者の追加（手順 2）
- ブランチの作成、コミット、push
- ドラフトの PR の作成と解除

**main ブランチは直接変更しない。** PR のマージ判断は担当者が行う。main は、担当者が対象 PR のマージを明示的に指示した場合だけ、`merge` スキルに従って実行できる。単なる作業依頼、Issue 対応依頼、PR 作成依頼はマージの許可とみなさない。

## 手順

手順 1〜8 は AI が、手順 9 以降の判断は人が行う。手順 12 の実行は、`merge` スキルに従って AI に指示できる。

### 定義

作業開始時に、作業対象リポジトリの「振り返りのタイミング」に従って定期分の実施時期を確認する。必要な振り返りは通常業務と別の作業として扱う。

1. 依頼の目的と完了条件を確かめ、必要な場合は Issue を作る（`issue-pr` スキル）。
   - 既存 Issue がある作業はそれを使う。計画のタスクに紐づく作業も Issue を使い、なければ作る。
   - それ以外で、目的と完了条件が依頼から明確で、調整や継続管理を要しない変更は、Issue を省いてよい。
   - 作業の順序や他の Issue の成果物への依存がありそうなときは、関連 Issue を調べる。先に完了が必要な Issue を blocked by に登録し、登録結果を確かめる。同じファイルを直すだけで順序が未定なら登録しない。後続の Issue を作るときも同じとする。

### 実行

2. 作業ブランチを作り、そこで変更する。Issue がある場合は、着手時に `gh issue edit Issue番号 --add-assignee @me` で担当者を追加する。既存の担当者は残す。
   - ブランチ名は内容を表す英小文字・数字・ハイフンとし、Issue があれば番号を先頭に付ける。例: `13-update-work-plan`、`fix-readme-link`。
3. Issue がある場合は、空コミットとドラフト PR を作り、「背景」に関連 Issue と作業の目的を書く（`issue-pr` スキル）。
4. 自ら、または委任で作業を実施する。Issue を省いた場合は、main が変更をコミット・push して PR を作る。

### 検証

5. 自ら、または verification への委任で、変更に応じた方法で中身を確かめる（`verification` スキル）。

### 確認

確認は、依頼を満たし、変更と検証結果を正しく説明しているかを確かめる。検証を省く作業でも確認は行う。

6. 変更を push し、PR 本文を整え（`issue-pr` スキル）、作業ログを書く（`work-log` スキル）。Issue があれば満たした要件にチェックを付ける。
   - 通常は事実とその場の対応を記録するところまでとする。振り返り・比較試行は作業対象リポジトリの「業務の改善方法」のタイミングで別の作業として行う。
7. 自ら、または confirmation への委任で確認項目を確かめ（`confirmation` スキル）、問題と確認したコミットをまとめる。問題は main が直す。
   - 再確認は、前回からの差分、PR 本文・Issue の更新と、指摘した問題の修正に絞る。前回のコミット・指摘・本文の更新箇所が分からなければ範囲を絞らない。
8. 確認の時間と残りの実行時間をログへ追記して push し、ドラフトなら解除する。時間記録だけの追記は再検証・再確認を要しない。
   - 担当者に PR の URL とレビュー項目の有無を伝える。PR 本文の内容は繰り返さず、範囲外の問題など必要な補足だけを添える。

### レビュー（人）

9. 担当者が PR 本文を読む。
10. 担当者がレビュー項目に答える。
11. 担当者だけで解消できない項目はレビュアーに依頼し、承認を得る。

修正が必要なら、担当者が main に直させ、必要な検証と手順 6〜8 をやり直す。レビュアーの指摘による修正は、担当者が確かめてから再レビューを依頼する。

### 完了処理

12. 担当者がマージを判断し、自分で実行するか、対象 PR を明示して main にマージを指示する。レビュアーを追加したときは、レビュアーの承認を得てからマージする。PR は squash マージし、マージしたら作業用のブランチを削除する。main が実行する場合は `merge` スキルに従う。

変更を直しても承認できない、または作業自体が不要になったときは、担当者が PR をマージせずに閉じる。Issue がある場合は、取りやめや定義し直しなどの扱いも決める。

## 参照先が見つからないとき

「振り返りのタイミング」「業務の改善方法」「時間の記録」などは作業対象リポジトリの文書を指す。見つからない場合は推測で補わず、見つからなかったことを担当者に伝える。
