# 作業の進め方

リポジトリのファイルを変える依頼は、変更の大小にかかわらず「作業」とする。作業は業務のどの段階でも行う。

依頼を受けたメインエージェント（main）は、**ファイルを変える前に、定義（手順 1）から始める。**

## 1. 業務の構成と置き場所

業務は、計画・仕様・実装で構成する。この順に行うとは限らず、省くことも、複数を同時に行うこともある。

| 段階 | 内容 | 置き場所 |
|---|---|---|
| 計画（plan） | どのように業務を進めるかを決める | `plan/` |
| 仕様（specification） | 満たすべきことを決める | `specification/` |
| 実装（implementation） | 仕様をもとに、リポジトリに変更を加える | 専用のフォルダを作らず、リポジトリのルート |

- 作業に関する内容でも、**必須の決まりは仕様**とし、`specification/業務/` に置く。
- 検証は業務の段階ではなく、各作業の手順 5 で行う（6 章）。条件や根拠を後で参照する価値がある検証の記録は `verification/` に置く。
- `plan/`・`specification/`・`verification/` は、下のフォルダ構造を合わせる。例: `plan/技術戦略/`、`specification/技術戦略/`、`verification/技術戦略/`
- `verification/` は、`specification/` の文書名のフォルダの下に、検証ごとのフォルダを作ってよい。例: `verification/技術戦略/情報取得/4-3_人員の情報取得方法/20261105_4社2年度での見本作成/`

`work/` の下は、上の 3 つのフォルダと構造を合わせない。

| 置き場所 | 置くもの |
|---|---|
| `work/実施/` | 実施に使うツール、テンプレート、ログなど |
| `work/実施/手引き/` | 仕様を補う、任意に参照する操作例や記載例。必須の決まりは定めない |
| `work/実施/log/` | 作業のログ（7 章） |
| `work/改善/` | 改善の補助資料 |

短い例は、参照のしやすさを踏まえて仕様と同じ文書にまとめてよい。決まりを二重に管理しない。

## 2. 役割と委任

作業の各手順とエージェントを一対一に対応させない。main が全体の文脈を保持し、自ら実行・検証・確認を担うか、必要に応じてサブエージェントへ委ねるかを判断する。3 種類すべてを呼ぶことや、手順ごとの起動は必須としない。別エージェントを使えない環境では main が各役割を担う。

| 役割 | 担い手 | 責任 |
|---|---|---|
| main | AI | 目的・完了条件・制約・進捗を保持し、作業、委任の判断、結果の統合、Issue・PR・ログの管理、担当者への説明 |
| execution | AI（サブエージェント） | 切り出された範囲の実装・調査。変更と結果、未完了の事項を main へ返す |
| verification | AI（サブエージェント） | 委ねられた検証（6 章）を行い main へ返す |
| confirmation | AI（サブエージェント） | 委ねられた確認（6 章）を行い main へ返す |
| 担当者 | 人 | main を動かす。レビュー項目に答え、マージを判断する。自分でマージするか、対象 PR を明示して main に実行を指示する |
| レビュアー | 人 | main では解決できず、担当者から回されたレビュー項目に答える。人数に制限はない |

担当者とレビュアーは、確認に AI を使ってよい。役割ごとの指示の置き場所と CLI の設定は、作業対象リポジトリの `specification/業務/実施/エージェント設定.md` に従う。

### 委任の判断

- 切り出せる実装・調査や並列作業 → execution が候補。
- 複雑な仕様、広い影響、安全性の判断など、独立した見直しが有益なとき → verification・confirmation が候補。
- その作業で必要かを判断する。小さな作業は main だけで完結してよい。
- 委任しても全体の判断と説明の責任は main に残る。戻った結果を依頼と照合して取り込む。
- 自ら担う場合も 6 章に従い、検証・確認を行った範囲と未確認の範囲を明示する。

委任時は、目的と完了条件、必要な制約・背景、担当範囲、対象ブランチと差分、関連する Issue・PR を渡す。変更を伴う並列作業では担当ファイルを分け、他の担当の変更を取り消さないよう伝える。

### サブエージェントが守ること

- 担当範囲に集中する。範囲外の変更や判断が必要なら、自分で進めずに main へ返す。
- 再委任、全体の Issue・PR・ログの管理、マージは行わない。
- 検証・確認で見つけた問題は、指示がなければ自分で直さず main へ返す。
- 結果には、変更箇所・根拠・検証結果・未完了の事項と時間の記録を含める。検証・確認では、検証・確認したコミットと、対象・対象外の範囲も含める。

## 3. 権限

main は次の操作を、担当者に聞かずに、作業の流れの中で必要になった時点で行う。

- Issue の作成と要件へのチェック
- Issue の blocked by へのブロックする Issue の追加（手順 1）
- Issue の assignee への担当者の追加（手順 2）
- ブランチの作成、コミット、push
- ドラフトの PR の作成と解除

**main ブランチは直接変更しない。** PR のマージ判断は担当者が行う。main は、担当者が対象 PR のマージを明示的に指示した場合だけ、8 章に従って実行できる。単なる作業依頼、Issue 対応依頼、PR 作成依頼はマージの許可とみなさない。

## 4. 手順

定義、実行、検証、確認、レビュー、完了処理の順に行う。手順 1〜8 は AI が、手順 9 以降の判断は人が行う。手順 12 の実行は AI に指示できる。

### 定義

作業開始時に、作業対象リポジトリの「振り返りのタイミング」に従って定期分の実施時期を確認する。必要な振り返りは通常業務と別の作業として扱う。

1. 依頼の目的と完了条件を確かめ、必要な場合は Issue を作る（5 章）。
   - 既存 Issue がある作業はそれを使う。計画のタスクに紐づく作業も Issue を使い、なければ作る。
   - それ以外で、目的と完了条件が依頼から明確で、調整や継続管理を要しない変更は、Issue を省いてよい。
   - 作業の順序や他の Issue の成果物への依存がありそうなときは、関連 Issue を調べる。先に完了が必要な Issue を blocked by に登録し、登録結果を確かめる。同じファイルを直すだけで順序が未定なら登録しない。後続の Issue を作るときも同じとする。

### 実行

2. 作業ブランチを作り、そこで変更する。Issue がある場合は、着手時に `gh issue edit Issue番号 --add-assignee @me` で担当者を追加する。既存の担当者は残す。
   - ブランチ名は内容を表す英小文字・数字・ハイフンとし、Issue があれば番号を先頭に付ける。例: `13-update-work-plan`、`fix-readme-link`。
3. Issue がある場合は、空コミットとドラフト PR を作り、「背景」に関連 Issue と作業の目的を書く（5 章）。
4. 自ら、または execution への委任で作業を実施する。Issue を省いた場合は、main が変更をコミット・push して PR を作る。

### 検証

5. 自ら、または verification への委任で、作業の変更が正しいかを確かめる（6 章）。

### 確認

6. 変更を push し、PR 本文を整え（5 章）、作業ログを書く（7 章）。Issue があれば満たした要件にチェックを付ける。
   - 通常は事実とその場の対応を記録するところまでとする。振り返り・比較試行は作業対象リポジトリの「業務の改善方法」のタイミングで別の作業として行う。
7. 自ら、または confirmation への委任で確認項目を確かめ（6 章）、問題と確認したコミットをまとめる。問題は main が直す。
8. 確認の時間と残りの実行時間をログへ追記して push し、ドラフトなら解除する。時間記録だけの追記は再検証・再確認を要しない。
   - 担当者に PR の URL とレビュー項目の有無を伝える。PR 本文の内容は繰り返さず、範囲外の問題など必要な補足だけを添える。

### レビュー（人）

9. 担当者が PR 本文を読む。
10. 担当者がレビュー項目に答える。
11. 担当者だけで解消できない項目はレビュアーに依頼し、承認を得る。

修正が必要なら、担当者が main に直させ、必要な検証と手順 6〜8 をやり直す。レビュアーの指摘による修正は、担当者が確かめてから再レビューを依頼する。

### 完了処理

12. 担当者がマージを判断し、自分で実行するか、対象 PR を明示して main にマージを指示する。レビュアーを追加したときは、レビュアーの承認を得てからマージする。PR は squash マージし、マージしたら作業用のブランチを削除する。main が実行する場合は 8 章に従う。

変更を直しても承認できない、または作業自体が不要になったときは、担当者が PR をマージせずに閉じる。Issue がある場合は、取りやめや定義し直しなどの扱いも決める。

## 5. Issue と PR

作業対象リポジトリの `.github/` のテンプレートに沿い、プレインランゲージ（読み手に合わせた明快で簡潔な文章）で書く。行数・文数・箇条書きの階層は固定しない。

### Issue

- タイトルは変更内容が分かる日本語の体言止めとし、`docs:` などの接頭辞は付けない。計画のタスクに由来する場合は Plan code と Task ID を付ける（後述）。
- 「概要」に目的と背景、「要件」に完了を判定できるチェックボックスを書く。前提や制約は関わる要件に添える。
- 満たした要件にはチェックを付ける。未達は残し、理由を PR の「レビュー項目」に書く。やり残しを後続 Issue にした場合は、PR の「変更」から参照する。結果は PR に書く。

### PR

タイトルは Issue があれば同じにし、なければ変更内容を表す日本語とする。本文は、作業のやり取りや差分を読んでいない人にも分かるよう、次の 3 項目で書く。

- **背景**：なぜ変更が必要か。関連 Issue があれば、完了するものは `Closes #番号`、参照だけなら `Refs #番号` を書く。
- **変更**：何を変え、どう確かめたか。影響・未検証の範囲・後続作業は必要に応じて含め、条件や根拠の詳細はファイルへ案内する。作業ログを置いたことは書かない。
- **レビュー項目**：人の判断・情報・権限が必要なことと、未達の要件。なければ「なし」と書く。
  - 先頭に判断してほしいことと採る案を示し、その項目だけで判断できる根拠・影響・参照先を添える。
  - 未達は、理由、代わりに確かめたこと、後続 Issue の有無を伝える。
  - 担当者が決めたことは聞き直さず、AI が確かめられることは先に確かめる。
  - 記載例は、作業対象リポジトリの「レビュー項目の例」を必要に応じて参照する。

### 計画との紐付け

計画ごとに Plan code、タスクごとに Task ID を付け、Issue と PR のタイトルを `{Plan code} {Task ID} {Issue 名}` とする。例: `TS 2.1 経営方針・業績の情報取得方法の整理`

- **Plan code**：計画ごとに 2 文字の英大文字。計画の内容を表す英単語の頭文字から付け、計画の間で重複させない。計画のデータ（例: `plan/技術戦略/plan.js`）の `code` に書く。例: `TS`（Technology Strategy、技術戦略）
- **Task ID**：階層を `.` でつないだ番号で、計画の中で一意にする。計画のデータの各タスクの `id` に書く。例: `1`、`2.1`。一度付けた Task ID は変えず、再利用しない。タスクを足すときは末尾の番号を付け、順序は日程で表す。
- 計画に由来しない Issue（業務の実施方法の改善など）には付けない。
- 1 つのタスクを複数の Issue に分けるときは同じ Task ID を付け、Issue 名で区別する。複数のタスクにまたがる Issue は、主となるタスクの Task ID をタイトルに入れ、ほかのタスクは概要に書く。
- Issue の PR は、紐付く Task ID の `status` を同じ PR で更新する。着手時に「進行中」、そのタスクの最後の Issue の PR で「完了」にする。紐付く Issue がないタスクは手で更新する。

## 6. 検証と確認

### 検証（手順 5）

作業の変更が正しいかを確かめる。

| 対象 | 確かめること |
|---|---|
| 実装 | 実装の結果が仕様の通りか |
| 仕様 | 仕様が正しいか。仕様をもとに実際に試すなどして確かめる |

- 仕様を変える作業は、実装を含まなくても仕様が正しいかを検証する。計画だけを変える作業は、検証する対象がないため省いてよい。
- 情報取得方法の試行など、仕様が正しいかを試すことが主な目的の作業も、その仕様の作業として扱う。試行は手順 5 で行い、手順 4 の変更は小さくても、なくてもよい。
- 誤字・リンク・簡単なスクリプト修正などの単発の確認は、方法と結果を PR の「変更」に書く。
- 情報取得方法の試行、外部環境での動作確認、仕様の妥当性の検討など、条件や根拠を後で参照する価値がある結果は `verification/` に置き、同じ PR に含める。この記録はさらに検証せず、手順 7 で確認する。
- 試していないことを試したように書かず、試せなかった範囲と理由を示す。
- 再検証は、前回検証したコミットからの変更と、それを要約・参照する箇所を対象とする。結果に検証したコミットと対象・対象外の範囲を書く。前回のコミットが分からなければ範囲を絞らない。

### 確認（手順 7）

依頼を満たし、変更と検証結果を正しく説明しているかを確かめる。検証を省く作業でも確認は行う。毎回、次を確かめる。

- 依頼を満たしているか。未達の要件と理由を明示しているか。
- PR の説明が実際の変更・検証結果と合い、作業の文脈を持たない人にも分かるか。
- 人の判断や追加作業が必要なことを伝えているか。すでに決まったことを聞き直していないか。

変更に関係するときは、リンク、配置、計画の状態、Issue との整合、ログの形式、`verification/` の記録が条件・根拠と結論を正しく示しているかも確かめる。分量を増やすだけの重複や不要な書式指定も見直す。

- 確かめた範囲と未確認の範囲を明示し、人の手助けが必要な部分をレビュー項目にする。AI が自分で確かめられることは、確かめてから示す。確認済みの項目を PR に列挙する必要はない。
- 再確認は、前回からの差分、PR 本文・Issue の更新と、指摘した問題の修正に絞る。前回のコミット・指摘・本文の更新箇所が分からなければ範囲を絞らない。

## 7. 作業のログ

main は、作業ごとにログを 1 ファイル書き、同じ PR に含める。Issue があれば `work/実施/log/Issue番号.md`、なければ `work/実施/log/pr-PR番号.md` とする。作業中に事実と時刻を控え、手順 6 でまとめ、やり直したときは追記する。新規ログのひな形は `work/実施/templates/log.md` を使う。

作業のタイトル、Issue があればその番号、PR 番号と、次を記録する。

- **起きたこと**：確認の指摘、レビューによる修正、担当者の訂正・不便・よかった点、迷った箇所、目的に照らした気づきを、根拠とともに書く。該当する事実がなければ「なし」。
  - 担当者の発言は要旨を根拠にできる。単なる案の選択は訂正に含めない。
  - チャットで伝えられた困り事やよかった点も、「記録して」と頼まれなくても状況とともにセッション終了前に残し、記録した要旨を短く伝える。
- **時間の記録**：各役割が作業中に計測し、main が集約する。項目と計測方法は作業対象リポジトリの「時間の記録」に従う。

残し方：

- 観測した事実とその場の対応を残す。原因の仮説や変更案、採否は「業務の改善方法」に従って扱う。
- 会話の全文、認証情報、個人情報は残さない。
- ログは検証・レビューの対象外とし、形式は手順 7 で確かめる。ログを置いたことは PR の「変更」に書かない。
- Issue がある作業では、計測と時間表の生成に `work/実施/tools/work_log.py` を使える。「利用手順」に従い各役割が計測し、main だけがログを生成する。管理マーカーの外の文章と手書きの時間記録は保持する。
- Issue のない作業はツールが対応していないため、手書きで記録する。

## 8. マージ（手順 12）

担当者が対象 PR のマージを明示的に指示した場合だけ、main が実行する。単なる作業依頼、Issue 対応依頼、PR 作成依頼はマージの許可とみなさない。

### 直前に確かめること

1. 対象リポジトリ・PR 番号が担当者の明示指示と一致し、PR が open でドラフトではないこと。
2. 最新の差分と head コミット、レビュー・チェック・マージ可否を取得し、レビュー項目への回答と必要な承認を確認する。
   - 指示後に差分が変わった場合は、変更内容を担当者へ伝えて改めてマージ指示を受ける。
   - 判断材料が足りない場合や、未解決の指摘・必須チェックの未完了がある場合は実行せず、その理由を伝える。

### 実行

```sh
gh pr merge PR番号 --squash --match-head-commit HEADのSHA --delete-branch
```

- 確認した head を `--match-head-commit` で指定する。
- `--admin` などで保護規則を迂回しない。
- `--auto` による将来のマージ予約も行わない。
- head が変わって拒否された場合は、再取得して担当者に変更を伝える。

### 実行後

- PR の状態を取得して結果を伝える。
- 環境の規則や権限で実行できない場合は、拒否された操作と理由、リポジトリ側か起動元・管理環境側か判別できる範囲を伝える。
- API・別ツール・スクリプトなどの別経路で迂回しない。

## 参照先が見つからないとき

「振り返りのタイミング」「業務の改善方法」「時間の記録」「利用手順」などは作業対象リポジトリの文書を指す。見つからない場合は推測で補わず、見つからなかったことを担当者に伝える。
