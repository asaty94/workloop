# 業務の構成と置き場所

業務は、計画・仕様・実装で構成する。この順に行うとは限らず、省くことも、複数を同時に行うこともある。

| 段階 | 内容 | 置き場所 |
|---|---|---|
| 計画（plan） | どのように業務を進めるかを決める | `plan/` |
| 仕様（specification） | 満たすべきことを決める | `specification/` |
| 実装（implementation） | 仕様をもとに、リポジトリに変更を加える | 専用のフォルダを作らず、リポジトリのルート |

- 作業に関する内容でも、**必須の決まりは仕様**とし、`specification/業務/` に置く。
- 検証は業務の段階ではなく、各作業の手順 5 で行う（`verification.md`）。条件や根拠を後で参照する価値がある検証の記録は `verification/` に置く。

## plan/・specification/・verification/ のルール

- 下のフォルダ構造は 3 つで合わせる。
  例: `plan/技術戦略/`、`specification/技術戦略/`、`verification/技術戦略/`
- `verification/` は、`specification/` の文書名のフォルダの下に、検証ごとのフォルダを作ってよい。
  例: `verification/技術戦略/情報取得/4-3_人員の情報取得方法/20261105_4社2年度での見本作成/`

## work/

`work/` の下は、3 つのフォルダと構造を合わせない。

| 置き場所 | 置くもの |
|---|---|
| `work/実施/` | 実施に使うツール、テンプレート、ログなど |
| `work/実施/手引き/` | 仕様を補う、任意に参照する操作例や記載例。必須の決まりは定めない |
| `work/実施/log/` | 作業のログ（`work-log.md`） |
| `work/改善/` | 改善の補助資料 |

- 短い例は、参照のしやすさを踏まえて仕様と同じ文書にまとめてよい。
- 決まりを二重に管理しない。決まりは仕様に、例は手引きに置く。
