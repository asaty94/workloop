# Issue と PR の書き方（手順 1・3・6）

Issue と PR は作業対象リポジトリの `.github/` のテンプレートに沿い、プレインランゲージ（読み手に合わせた明快で簡潔な文章）で書く。行数・文数・箇条書きの階層は固定しない。

## Issue

- タイトルは変更内容が分かる日本語の体言止めとし、`docs:` などの接頭辞は付けない。計画のタスクに由来する場合は Plan code と Task ID を付ける（後述）。
- 「概要」に目的と背景、「要件」に完了を判定できるチェックボックスを書く。前提や制約は関わる要件に添える。
- 満たした要件にはチェックを付ける。未達は残し、理由を PR の「レビュー項目」に書く。
- やり残しを後続 Issue にした場合は、PR の「変更」から参照する。
- 結果は PR に書く。

## PR

タイトルは Issue があれば同じにし、なければ変更内容を表す日本語とする。

本文は、作業のやり取りや差分を読んでいない人にも分かるよう、次の 3 項目で書く。

- **背景**：なぜ変更が必要か。関連 Issue があれば、完了するものは `Closes #番号`、参照だけなら `Refs #番号` を書く。
- **変更**：何を変え、どう確かめたか。影響・未検証の範囲・後続作業は必要に応じて含め、条件や根拠の詳細はファイルへ案内する。作業ログを置いたことは書かない。
- **レビュー項目**：人に判断や手助けを求めること（次節）。なければ「なし」と書く。

## レビュー項目の書き方

人の判断・情報・権限が必要なことと、未達の要件を書く。

- 先頭に判断してほしいことと採る案を示し、その項目だけで判断できる根拠・影響・参照先を添える。
- 未達は、理由、代わりに確かめたこと、後続 Issue の有無を伝える。
- 担当者が決めたことは聞き直さない。
- AI が確かめられることは先に確かめる。

記載例は、作業対象リポジトリの「レビュー項目の例」を必要に応じて参照する。

## 計画との紐付け

計画のタスクと Issue を紐付けるため、計画ごとに Plan code、タスクごとに Task ID を付け、Issue と PR のタイトルに入れる。

- タイトルの形式は `{Plan code} {Task ID} {Issue 名}`。例: `TS 2.1 経営方針・業績の情報取得方法の整理`
- **Plan code**：計画ごとに 2 文字の英大文字。計画の内容を表す英単語の頭文字から付け、計画の間で重複させない。計画のデータ（例: `plan/技術戦略/plan.js`）の `code` に書く。例: `TS`（Technology Strategy、技術戦略）
- **Task ID**：階層を `.` でつないだ番号で、計画の中で一意にする。計画のデータの各タスクの `id` に書く。例: `1`、`2.1`
  - 一度付けた Task ID は変えず、再利用しない。タスクを足すときは末尾の番号を付ける。順序は日程で表す。
- 計画に由来しない Issue（業務の実施方法の改善など）には、Plan code と Task ID を付けない。
- 1 つのタスクを複数の Issue に分けるときは、同じ Task ID を付け、Issue 名で区別する。
- 複数のタスクにまたがる Issue は、主となるタスクの Task ID をタイトルに入れ、ほかのタスクは概要に書く。
- Issue の PR は、紐付く Task ID の `status`（計画のデータの状態）を同じ PR で更新する。着手時に「進行中」、そのタスクの最後の Issue の PR で「完了」にする。紐付く Issue がないタスクは手で更新する。
